세션 진행 평가

Agent 1: 빠른 자율 실행형

Agent 1은 harden-issue 스킬 계약을 확인하고, 처음에는 이슈 파일 경로를 요구했다. 경로를 받은 뒤에는 issue file, issue tracker guide, CONTEXT-MAP, Web CONTEXT, PRD, ADR, hook/API/UI/test 파일을 폭넓게 읽었다. 이후 "white-user lifecycle 완성"으로 scope를 고정하고 바로 AC hardening과 구현을 진행했다.

  • 장점: 환경을 실제로 읽고, Web이 Terminal state를 소유한다는 도메인 계약을 파악했다.
  • 장점: implementation까지 밀고 가는 속도가 빠르고, 마지막에 backend와 frontend smoke까지 확인했다.
  • 약점: UX/API 결정들을 사용자에게 선택지로 묻기보다는 스스로 확정했다.
  • 약점: 완료 후 PR/commit 형태로 정리하지 않았고, 평가 시점에 dirty worktree로 남아 있다.

Agent 2: 명시적 의사결정형

Agent 2는 hardening 자체를 독립 작업처럼 다뤘다. Terminal UI, label depth, 50-move detection, move-list layout, New Session 노출 시점, humanColor='black' 범위, reset race, terminal type, test coverage를 round별로 질문하고, 결정된 내용을 이슈 AC에 먼저 반영했다.

  • 장점: 사용자의 선택을 거쳐 AC를 구체화했기 때문에 구현 기준이 리뷰 가능한 계약으로 남았다.
  • 장점: hardening commit과 implementation commit을 분리해 변경 의도가 잘 드러난다.
  • 장점: PR #25를 열고 manual smoke를 별도 체크리스트로 남겼다.
  • 약점: chess.js 1.4.0에 isDrawByFiftyMoves()가 있는데도 "전용 API가 없다"고 판단했다.

세션 방식의 승자: Agent 2. 이 작업은 단순 코드 추가가 아니라 Web CONTEXT의 "Terminal state" 개념을 UI와 hook API로 승격하는 작업이었다. 이런 경우에는 Agent 2처럼 tradeoff를 먼저 잠그는 진행 방식이 더 적절하다.

프로그래밍 품질 평가

Agent 1 품질 분석

7.6 기능 완성도와 race 방어는 좋지만, abstraction 경계는 다소 얇다.

  • 좋음: isDrawByFiftyMoves() 전용 API를 사용해 의도를 정확히 표현했다.
  • 좋음: reset 시 requestIdRef 증가로 stale engine response를 무효화했고 테스트도 있다.
  • 좋음: 기존 isGameOver 호환 필드를 유지해 migration risk가 낮다.
  • 아쉬움: MoveList가 App.tsx 내부에 있어 테스트 가능한 pure boundary가 없다.
  • 아쉬움: terminal value가 flat string이라 checkmate winner 같은 의미 정보를 타입으로 강제하지 못한다.
  • 아쉬움: New Session 버튼이 항상 보이는 선택은 원래 broad AC에는 가능하지만, accidental reset UX에 약하다.

Agent 2 품질 분석

8.7 타입 모델링, UI 분리, 테스트 경계가 더 좋다.

  • 좋음: TerminalState를 discriminated union으로 모델링해 UI switch가 자연스럽다.
  • 좋음: TerminalBanner, MoveList, pairSanHistory를 분리했다.
  • 좋음: move-list pairing helper에 별도 unit test가 있어 회귀 탐지가 쉽다.
  • 좋음: checkmate winner를 타입에 포함해 결과 라벨을 정확히 만들 수 있다.
  • 아쉬움: chess.js의 50-move 전용 API 존재를 놓쳐 isDraw() fallback과 부정확한 주석/커밋 설명을 남겼다.
  • 아쉬움: reset test는 completed engine reply 후 reset만 검증하고, Agent 1처럼 stale in-flight reply case를 직접 검증하지 않는다.

중요한 nuance: Agent 2가 종합적으로 더 낫지만, 50-move rule 구현만 보면 Agent 1이 더 정확하다. Agent 2의 fallback은 현재 predicate order상 실사용에서는 통과 가능성이 높지만, dependency API를 잘못 파악한 설명은 장기 유지보수 문서로는 품질 감점이다.

최종 결론

Agent 2를 기준 구현으로 삼는 것이 맞다. Agent 2는 세션을 더 잘 운영했고, 프로젝트 문서의 언어를 타입과 UI 구조로 더 잘 번역했으며, PR로 넘기기 좋은 형태까지 정리했다. 프로그래밍적으로도 component/helper/test 경계가 더 좋다.
