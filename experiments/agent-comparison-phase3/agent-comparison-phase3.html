3. Phase 3 정답 기준

출처: .scratch/playlike-chess/issues/01-random-move-tracer.md Phase 3 섹션.

  1. Session 이 다섯 가지 Terminal-state 조건 각각에서 올바르게 종료되고 UI 에 표시된다 (checkmate / stalemate / threefold repetition / 50-move rule / insufficient material).
  2. 페이지 리로드 없이 새 Session 을 시작할 수 있다.
  3. Session 을 1수부터 Terminal state 까지 end-to-end 로 막힘없이 플레이할 수 있다.
  4. SAN (Standard Algebraic Notation) move list 가 Session 중 표시된다.

추가 가드레일 (메모리 + Phase 2 컨벤션):

  • Promotion picker 는 q / r / b / n 모두 지원 — auto-queen 금지.
  • 5-way terminal 판정 predicate 순서가 정확해야 한다 (chess.js isDraw() 가 stalemate · threefold · insufficient material 도 참이므로).
  • Phase 2 의 컴포넌트 분리 패턴 (components/Board.tsx, components/PromotionPicker.tsx) 을 잇는다.

// useChessSession.ts:49
function detectTerminal(chess: Chess): TerminalState | null {
  if (chess.isCheckmate()) {
    return { kind: 'checkmate', winner: chess.turn() === 'w' ? 'black' : 'white' }
  }
  if (chess.isStalemate()) return { kind: 'stalemate' }
  if (chess.isThreefoldRepetition()) return { kind: 'threefold-repetition' }
  if (chess.isInsufficientMaterial()) return { kind: 'insufficient-material' }
  if (chess.isDraw()) return { kind: 'fifty-move-rule' }   // fallback
  return null
}

export function pairSanHistory(history: HistoryEntry[]): string[] {
  const lines: string[] = []
  for (let i = 0; i < history.length; i += 2) {
    const moveNumber = i / 2 + 1
    const white = history[i].san
    const black = history[i + 1]?.san
    lines.push(black ? `${moveNumber}. ${white} ${black}` : `${moveNumber}. ${white}`)
  }
  return lines
}

6. 평가 — 네 축

6.1 세션 진행 방식

두 에이전트 모두 harden-issue 스킬의 "경로를 추정하지 않고 사용자에게 묻는다" 계약을 정확히 지켰고, 분해된 AC 수도 11–12 로 거의 같다. 결정적 차이는 세션을 어떻게 종료시키는가 였다. W1 은 구현 코드는 만들어 두고도 커밋·PR·체크박스 갱신 중 어느 것도 마치지 못한 채 자기 raw JSONL 경로를 출력하면서 끝났다 (사용자가 결과를 보려면 working tree 를 직접 확인해야 함). 반면 W2 는 docs/feat 의도 분리 2-커밋과 PR #25 생성으로 자기 결과물을 외부에서 검토 가능한 상태로 닫았다.

Winner: W2 · Claude

단, "AC 12개 분해"라는 산출물 자체는 W1 의 hardening 깊이가 약간 더 세밀했다. hardening 만 평가한다면 동률에 가깝고, "세션이 약속한 다음 단계까지 도달했는가" 라는 운영 관점에서 W2 의 우세가 명확하다.

6.2 프로젝트 적합성

Phase 2 는 이미 src/web/app/components/Board.tsx, components/PromotionPicker.tsx 라는 분리 패턴을 정착시켰다. W2 는 이 패턴을 그대로 이어 components/TerminalBanner.tsx + components/MoveList.tsx + 별도 moveList.ts 헬퍼로 확장했다. W1 은 MoveList 를 App.tsx 안에 인라인 함수로 정의해 같은 컴포넌트 그래뉼래리티를 깬다. 또 W2 는 helper 단위 테스트(moveList_test.ts)까지 Phase 2 의 apiClient_test.ts · useChessSession_test.ts 패턴에 맞춰 추가했다. 이슈 트래커 가드레일(## Acceptance criteria 체크박스 갱신) 도 W2 만 커밋으로 반영했다.

Winner: W2 · Claude

6.3 프로그래밍 우수성

축별로 정직하게 짚어 보면:

  • 타입 표현력 — W2 의 discriminated union ({ kind: 'checkmate'; winner: Color }) 이 W1 의 literal union보다 우수하다. 체크메이트의 승자라는 도메인 정보를 타입 안에 안전하게 동반시킨다.
  • 5-way 판정 robustness — 이 축에서는 W1 이 약간 더 보수적 이다. W1 은 isDrawByFiftyMoves() 라는 전용 predicate 를 직접 호출한다. W2 는 같은 라인의 주석에 "chess.js v1 exposes no dedicated fifty-move-only predicate" 라고 적었지만, 실제로 chess.js v1.x 에는 isDrawByFiftyMoves() 가 존재한다. W2 의 fallback (다른 draw predicate 들이 모두 false 라면 isDraw() 는 fifty-move 일 것이라는 가정) 은 현재 chess.js 동작 하에서는 옳지만 미래 변경에 더 취약하다.
  • 코드 구조 — W2 가 컴포넌트·헬퍼·테스트를 분리해 단일 책임이 더 명확하다. W1 의 인라인 MoveList 는 v1 에서는 짧지만 곧 hot path 가 되면 분리를 강제당할 자리다.
  • 테스트 커버리지 — 두 쪽 모두 hook 레벨 5-way terminal 테스트와 reset 무효화 테스트를 갖췄다. W2 는 그 위에 helper 단위 테스트(짝수·홀수·빈 입력)를 추가한 점이 약간 더 두텁다.
  • 경계 처리 — W2 의 requestEngineMove() 422 defensive 경로(로컬 terminal 을 네트워크 에러로 가리지 않음) 와 resetSession 의 비행 응답 폐기는 W1 의 동등 동작과 같지만, W2 쪽은 주석으로 의도를 명시한다.

Winner: W2 · Claude (단, 판정 predicate 만 보면 W1 이 더 안전)

6.4 종합

네 축 중 1번(진행 방식), 2번(프로젝트 적합성), 3번(프로그래밍 우수성) 모두 W2 가 앞선다. W2 의 우세는 한 줄로 요약하면 "약속을 외부 산출물로 닫았다" — 코드가 워크트리에 있을 뿐 아니라 커밋 메시지, 분리된 컴포넌트, 단위 테스트, PR 설명을 통해 외부에서 검증 가능한 상태가 됐다는 점이다. W1 은 같은 26분 동안 동등한 코드를 만들었지만 그 코드를 working tree 에만 남겨두어 다음 작업자(혹은 같은 에이전트의 다음 세션) 가 다시 발견하고 정리해야 하는 상태로 두었다.

최종 Winner: W2 · Claude

  if (chess.isDraw()) return { kind: 'fifty-move-rule' }
  return null
}

export function pairSanHistory(history: HistoryEntry[]): string[] {
  const lines: string[] = []
  for (let i = 0; i < history.length; i += 2) {
    const moveNumber = i / 2 + 1
    const white = history[i].san
    const black = history[i + 1]?.san
    lines.push(black ? `${moveNumber}. ${white} ${black}` : `${moveNumber}. ${white}`)
  }
  return lines
}
